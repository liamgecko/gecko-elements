# Categories list migration evidence

28 September 2026. Status: implemented in the Admin working tree; live behaviour acceptance incomplete. Read the [migration plan](../README.md) first. Source baseline: current Admin `e0a13ee90` plus its pre-existing working-tree changes and the signed-in `/admin/settings/categories` page. Target: `/admin/elements/settings/categories`, uncommitted. The earlier `elements-experiment` branch was not used.

## Scope and current-app behaviour

`Modules/Categories/index.jsx` and `state.jsx` use `getCategories` through `categoriesRequest({ include: 'user', ...params })`. Initial route resolution and later ListView requests fetch `/categories` with `page`, `per_page`, `keyword`, `order_by`, `include=user` and optional `type`. The current table displays Title, raw Type and Created by; all three cells link to `/admin/settings/categories/{id}`. The only row menu action is Remove category, guarded by a confirmation, then DELETE `/categories/{id}`, success/error toast and list refresh. Header offers New category at `/admin/settings/categories/new`, Settings → Categories breadcrumbs and a favourite. Search submits a keyword; the Type filter offers Event or Template and requires Apply filter. The current default is 15 rows per page with server total and page navigation. The live Stage 281 baseline showed 1,033 total rows before filtering.

The Elements list uses the public Data table remote interface with the same category request, response rows and server total. It owns the requested search, Type filter, Title/Type/Created by column toggles (Title stays visible), row actions, native full-cell links and pagination. Filter changes apply when selected through the Elements control; its two-value selection means all types. Search, filter, page and page size live in the route query, survive refresh and do not replace the mounted shell. Settings → Categories and the Categories → Settings breadcrumb navigate internally. The first request now runs after the page mounts, so initial navigation and refresh render the Data table's built-in skeleton rows under its persistent header and toolbar. Its default page-size row count, fixed column widths, one-line cell placeholders and action-control placeholder reserve the loaded row dimensions. The table keeps previous rows while a query updates and ignores obsolete responses. A query changing from zero results to another dataset shows the Data table loading body rather than a false no-data message. Server errors use the table's Retry control. New/edit still open their canonical existing-app pages; those forms are outside this slice.

The existing remove Command navigates to the legacy React document after deletion, so the Elements page uses the same authenticated `Delete` request service, existing request-error formatter and Elements toast callbacks directly. Successful deletion refreshes the current query, moving to the prior page if the deleted row was alone on a later page. No legacy route, ListView or shared component was changed for this slice. The new route, destination mapping and query adapter are under `src/Elements`; English/Spanish locale additions are the only files outside that partition.

The user subsequently requested immediate search/filter requests and a bounded page-number dropdown. Categories no longer delays keyword requests by 250 ms; the Type filter was already immediate. Elements Data table pagination now caps its page-number Select menu at 18rem or the available viewport height. The verified next.5 release contains only this library change relative to published next.4, and Admin now installs that exact private version. Admin's running Vite server initially kept serving its pre-install dependency bundle; restarting it with `npm start -- --force` rebuilt the bundle, and a live reload showed the page-number menu capped to roughly nine visible options with internal scrolling.

## Verification and remaining work

- `npm run build:development -- --logLevel error` passed after the final implementation; TypeScript and both Vite entries compiled. No automated Admin migration tests were added or run, per user direction.
- The initial Categories route resolve was removed so the table can mount before its request completes. The development build passed after this loading change; a fresh browser timing/height check is still outstanding. The global authentication startup screen and lazy route-chunk fallback are separate from the table request and remain as previously scoped.
- After the immediate-search change, the Admin development build passed. The next.5 package passed its required release verification; after installation, the Admin development build passed and its installed package contains the 18rem CSS rule. The forced Vite rebuild picked up the class, and the signed-in browser showed the capped dropdown after refresh. No automated Admin migration tests were run. Browser verification of the new search timing remains outstanding.
- In the signed-in Stage 281 browser, the Elements first page showed the same first 15 records and 1,033 total as the existing page. Searching “Scott” returned six server results and updated `keyword` in the URL. Selecting Event updated `type=event` and returned 1,008 records. Pagination moved to page two with different records; changing page size to 25 reset to page one and updated `perPage=25`. Refresh preserved the Event filter and 25-row page size.
- A Template deep link selected the Template filter and returned 25 template records. The column menu exposed Type and Created by while retaining Title. Toggling Type hid and restored that column. Clicking a row opened its canonical existing-app category editor; New category exposed the canonical create URL. The row menu opened the Remove category confirmation, and Cancel left the data unchanged. A no-match search displayed the Elements empty state. Its combined clear action removed both keyword and Type query parameters and restored the unfiltered 1,033 records.
- Browser Back and Forward between pages one and two restored both the URL and matching records. This check exposed and resolved a stale-row bug when returning to the route's initial query. Refresh preserved the Event filter and 25-row page size. Settings → Categories and the Categories breadcrumb → Settings kept the Elements document and shell. The last loading adjustment also prevents a no-data flash when clearing a query with zero results.
- Live deletion, DELETE failure, GET failure/Retry, favourite mutation and a deliberately slowed response race are not yet verified. Do not mark parity verified until these are checked. No live category was deleted during this investigation. Elements Search currently hardcodes the clear button's accessible label in English; Spanish translation of that library-owned control remains a library capability gap.
