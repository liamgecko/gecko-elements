# Gecko Admin migration to Elements: assessment and evidence

9 September 2026. This is an assessment for migration planning, not an implementation or approval of a particular migration design.

Follow-up: [Rollout options comparison](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/docs/ui-migration/rollout-options.md>) evaluates the gradual-adoption baseline below against a complete cutover and a whole-app pilot. It also identifies an additional global public stylesheet and release/rollback considerations. No rollout strategy has been selected.

## Assessment

**Migrating to Elements is feasible and is a sensible long-term direction. It is a substantial product-interface migration with some library readiness work first. It is not an import-path replacement.** The existing Admin app has useful shared UI wrappers and established data hooks, so there is no evidence that its API layer, authentication, router or business state must be rewritten to adopt Elements.

The biggest advantages are a Gecko-owned component API, documented composition and accessibility expectations, and one implementation shared by prototypes and production. The biggest hazards are global CSS ownership, incompatible runtime assumptions, and losing behavior hidden inside existing wrappers. A prefix is useful, but does not solve those hazards on its own.

My recommendation is to prepare Elements as an externally consumable library, prove coexistence in an isolated integration fixture, and migrate complete workflows behind a rollback flag. Keep Admin's domain logic while replacing its presentation through reviewed composition seams. Treat React Bootstrap removal, legacy CSS removal and retirement of other vendors as separate milestones.

## 3. Advantages worth preserving

1. **Gecko can own a stable interface instead of exposing Bootstrap throughout products.** Public subpath imports and contracts already define approved usage, and the dependency policy assigns each capability to an implementation. That should reduce future vendor migration cost if applications keep importing Gecko interfaces. [Guide](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/README.md:17>), [dependency ownership](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/docs/dependencies.md:1>).
2. **Production can benefit directly from prototype work.** Buttons, fields, dialogs, tables and conversation components are shared implementation, not just screenshots. Keep that feedback loop, while validating production data volume, permissions, translations and failure states separately. [Repository structure](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/README.md:5>), [Data table contract](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/docs/data-table.md:298>).
3. **There is a stronger accessibility and state model to build on.** Contracts describe focus, validation, loading and compound composition. Base UI supplies accessible primitives; this is a foundation, not proof of end-to-end accessibility after product composition. [Button contract](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/docs/button.md:98>), [Dialog contract](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/docs/dialog.md:120>), [Base UI overview](https://base-ui.com/react/overview/about).
4. **Existing App wrappers can retain domain behavior while their rendering changes.** There is already a compatibility example: `ReactBootstrapForm` copies Form statics and overrides Select with react-select. Preserve product adapters where useful, with approved Elements components underneath; avoid a permanent duplicate UI library or wrappers that restyle Elements. [Existing adapter](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/src/Components/Ui/Form/ReactBootstrapForm/index.jsx:1>), [Elements composition rules](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/README.md:47>).

## 4. Prefixing and CSS coexistence: evidence, not assumptions

### Measured conflicts

The compiler probe found **111 overlapping exact simple class selectors**. Examples include `border`, `rounded`, `container`, `table`, `gap-2`, `p-2`, `text-primary` and `bg-primary`. This is a lower-bound selector inventory from Elements' explicit source scan, not a count of 111 distinct regressions. Some declarations currently agree; others do not, and inheritance can make identical-looking spacing rules diverge. Full results are in the linked JSON.

Legacy spacing is Gecko's custom pixel scale, not assumed stock Bootstrap spacing. Its `.p-2` and `.gap-2` are `8px !important`; Elements uses the Tailwind spacing variable. Legacy `.border` sets width, style and color with `!important`, so it can override Elements' component border colors even where the numeric width matches. [Legacy utilities](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/src/Styles/gecko-react-bootstrap.css:14265>), [spacing configuration](</Users/liamyoung/Repos/Gecko-Admin-Web-App/Design/src/Styles/_variables.scss:408>), [Elements button classes](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/button.tsx:9>).

The actual copied CSS sets `--gecko-root-font-size: 14px`, applies it to `:root`, and also sets `html { font-size: 87.5% }`. Elements alone used a 16px browser root in the probe. [Copied CSS](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/src/Styles/gecko-react-bootstrap.css:204>), [root rules](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/src/Styles/gecko-react-bootstrap.css:232>).

| Synthetic probe | Elements alone | Legacy + Elements, either order |
| --- | --- | --- |
| Root font size | 16px | 14px |
| `div.h-8.text-sm`: height | 32px | 28px |
| Same element: text size | 14px | 12.25px |
| Same element inside a wrapper with `font-size:16px` | 32px / 14px | 28px / 12.25px |
| `h2.text-sm`: text size | 14px | about 18px |

**A wrapper font size does not repair rem sizing. Loading Elements last does not repair the cascade.** The heading result demonstrates legacy unlayered element styling winning over a new layered utility. Normal unlayered author rules outrank normal layered rules; `!important` introduces its own layer precedence. Specificity or import order alone is not a complete plan. [CSS layer rules](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@layer).

### What a prefix would and would not do

I recommend **one fixed library-wide prefix**, with `ge:` as an illustrative name to agree during planning. Tailwind v4 uses syntax such as `ge:flex` and `ge:hover:bg-primary`, configured through `prefix(ge)`. Consumers of a Button need no prefix prop; its internal classes belong to the library. Authors using approved layout utilities would use the chosen namespaced utilities. [Tailwind prefix documentation](https://tailwindcss.com/docs/upgrade-guide#using-a-prefix).

This is not an automatic rewrite of current component strings. A probe changing only the existing Tailwind import to `prefix(ge)` failed with `Cannot apply unprefixed utility class bg-primary`. The source contains CVA strings, literal className values, group/peer selectors and `@apply` rules; the shared `cn` uses default `twMerge`. All need coordinated handling, including prefix-aware merging and generation of the actual static class candidates. [Global stylesheet](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/styles/globals.css:1>), [class merge helper](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/lib/utils.ts:1>), [literal classes outside cn](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/select.tsx:80>), [tailwind-merge configuration](https://github.com/dcastil/tailwind-merge/blob/main/docs/configuration.md).

| Approach | Assessment |
| --- | --- |
| Native fixed Tailwind prefix plus a reviewed source migration | Preferred starting point: explicit and aligned with Tailwind tooling. Update components, CSS, examples, contracts and caller layout classes together. |
| Build-time automatic namespace transform | Possible if authoring ergonomics justify maintaining it. Must transform generated CSS and every relevant class reference consistently, including variants, selectors and third-party markup. A blind string prefixer is unsafe. |
| Prefix inside `cn()` at runtime | Insufficient: many literals bypass `cn`, arbitrary classes must be distinguished, and Tailwind needs discoverable candidates before runtime. |
| Scoped wrapper alone | Useful boundary, but does not block incoming legacy element selectors, reset rem units, or capture body portals. |
| Shadow DOM | Stronger selector isolation, but document-root rem sizing and portal placement still require work; third-party editors and integration become more complex. Not my default recommendation. |
| Separate document/iframe or separately loaded app route | Stronger CSS and root-unit boundary. Useful for a coarse isolated experience, with real costs in routing, focus and state communication. A client-side route alone does not ensure old CSS is unloaded. |

Prefixing Tailwind-generated variables does not automatically rename handwritten tokens such as `--background`, custom classes such as `.scrollbar-scroll-area`, keyframes or `.dark`. Legacy already prefixes many variables with `--gecko-`; its class selectors remain unprefixed. Inventory actual collisions rather than assuming every variable conflicts. [Elements tokens/custom classes](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/styles/globals.css:147>), [legacy variable prefix](</Users/liamyoung/Repos/Gecko-Admin-Web-App/Design/src/Styles/_variables.scss:390>).

### The missing coexistence contract

Before production adoption, agree and prove:

- **Baseline styles in both directions.** Split opt-in document reset/fonts from reusable component styles, tokens and utilities; establish an Elements root and portal scope. Tailwind Preflight is included by today's import, and Elements adds universal, body and html rules. Disabling Preflight alone can leave components relying on missing normalization. Layering legacy CSS or containing its selectors is a possible strategy, but must be tested against existing `!important` rules. [Elements base layer](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/styles/globals.css:436>), [Tailwind Preflight](https://tailwindcss.com/docs/preflight).
- **Root-unit policy.** Choose whether to normalize the shared document to 16px while preserving legacy dimensions, create a carefully specified interim unit conversion for Elements, or initially isolate a complete experience in another document. Each has costs. Do not silently shrink Elements or change the global root and hope existing rem-based pages survive.
- **Overlay policy.** Legacy defaults span z-index 1000–1090; its react-select wrapper portals to body at 2147483647. New Dialog/Select use `z-50`. Define stacking, portal destination, theme scope, nested focus ownership, escape/outside click and scroll lock together. [Legacy scale](</Users/liamyoung/Repos/Gecko-Admin-Web-App/Design/src/Styles/_variables.scss:1416>), [react-select portal](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/src/Components/Ui/Form/Fields/ReactSelect/index.jsx:66>), [new Dialog](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/dialog.tsx:70>), [new Select](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/select.tsx:80>).
- **Supported portal API.** New `DialogContent` internally creates its portal and accepts Popup props; new `SelectContent` similarly owns Portal/Positioner. An external scope/provider is not currently a documented common solution. A migration may need a reviewed library-level portal/theme interface. Mixing focus engines is an identified risk, not a runtime failure reproduced here. Legacy Drawer explicitly disables focus enforcement. [Dialog implementation](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/dialog.tsx:46>), [Select implementation](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/select.tsx:65>), [legacy Drawer](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/src/Components/Ui/Drawer/index.jsx:86>).

These policies belong in Elements' integration contract, not in per-screen overrides that contradict its existing styling contracts.

## 5. Runtime and packaging readiness

**The complete current library cannot be treated as a supported drop-in dependency in the unchanged React 18 app.** React and ReactDOM are currently ordinary Elements dependencies at `^19.2.4`. An external install can introduce a second React copy, which is not a supported way to mix these components in one tree. A production library should declare its tested React peer range and externalize React from any package bundle. [Manifest](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/package.json:27>).

There are two possible tracks:

- **Upgrade Admin to React 19 first**, separately from the visual migration. This aligns with Elements, but the actual `react-beautiful-dnd` usage must be addressed: its locked peer range stops at React 18. Broad peer declarations on other packages do not prove functional React 19 compatibility. [DnD lock entry](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/package-lock.json:8825>), [actual sortable usage](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/src/Components/SortableList/index.jsx:6>).
- **Deliberately support a React 18 subset of Elements during migration.** Base UI itself supports React 17+, so it is not intrinsically the blocker. However, the full dependency set is not React-18-compatible by declaration: `@shadcn/react`, used by Message scroller, declares React >=19. Ordinary function wrappers such as Input also need ref compatibility review; simply widening peer ranges is insufficient. [Base UI](https://base-ui.com/react/overview/about), [shadcn lock entry](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/package-lock.json:3291>), [Message scroller import](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/message-scroller.tsx:3>), [Input wrapper](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/components/input.tsx:24>), [React ref change](https://react.dev/blog/2024/12/05/react-19#ref-as-a-prop).

For external distribution, I favor compiled ESM plus type declarations and compiled component CSS, with React kept external. This lowers consumer dependence on the library's compiler setup. If consumers need additional Tailwind layout utilities, document that optional pipeline and its scanning boundaries. A source package can also work with Vite; it is a deliberate tighter coupling, not an architectural impossibility.

Required release work includes versioning, restricted internal distribution, CSS/font assets, export/type resolution, CSS side-effect handling, release notes, rollback to a pinned version, and a clean external consumer fixture without source aliases. Today's `private: true` prevents npm publication; it does not prevent local workspace or tarball use. Existing CI builds applications, not a releasable UI artifact. [Manifest exports](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/package.json:54>), [current CI](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/.github/workflows/pages.yml:38>), [font assets](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/assets/fonts/satoshi.css:1>).

There is **no demonstrated need for an App Vite major upgrade just to add Tailwind**: the locked Tailwind Vite plugin accepts Vite `^5.2.0`. Keep the Sass pipeline and Tailwind CSS entry separate; Tailwind v4 is not intended to run inside Sass. [Plugin peer range](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/package-lock.json:3783>), [App config](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/vite.config.js:27>), [Tailwind compatibility](https://tailwindcss.com/docs/compatibility).

Source scanning needs attention if choosing source distribution. The stylesheet's explicit `../../../apps` path resolves from `packages/ui/src/styles` to `packages/apps`, not the repository's root `apps`; the self-source covers library TS/TSX. Existing automatic scanning and aliases can mask these assumptions. Admin also has JSX/JS files. Specify package and consumer sources deliberately; node_modules is ignored by default scanning. [Current directives](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/styles/globals.css:8>), [Tailwind source detection](https://tailwindcss.com/docs/detecting-classes-in-source-files).

Other release concerns: both systems define the Satoshi-Gecko family through different loading arrangements; Elements also imports Google-hosted Geist Mono and its Emoji picker contract records a runtime CDN. Confirm production font assets/network policy rather than discovering them after rollout. Tailwind's browser baseline is Chrome 111+, Safari 16.4+, Firefox 128+; the actual supported customer/browser policy remains unknown. These are review gates, not proven organisational blockers. [Legacy font import](</Users/liamyoung/Repos/Gecko-Admin-Web-App/Design/src/Styles/bootstrap.scss:4>), [Elements imports](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/src/styles/globals.css:1>), [Emoji dependency policy](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/docs/dependencies.md:45>), [browser requirements](https://tailwindcss.com/docs/compatibility).

## 7. Blockers versus risks

| Classification | Item | What clears it |
| --- | --- | --- |
| Gate before supported shared-tree adoption | React 18/19 ownership and dependency compatibility | Chosen/tested React track, peer dependencies and a single compatible React runtime. |
| Gate before dependable external release | Package artifact and external consumption currently unproven | Versioned distribution plus a clean external build/import/CSS fixture. |
| Demonstrated blocker to naive dual-global-CSS adoption | Root sizing, unlayered rules and overlapping utilities | A coexistence contract proven by CSS and interaction tests. A prefix alone is not sufficient. |
| Blocker for migrating server-backed list screens through today's DataTable | No approved controlled/server table interface | Library enhancement or approved lower-level composition preserving remote data semantics. |
| Blocker for affected field/translated screens | Async/creatable and some internal localization interfaces missing | Capability and locale interfaces, examples and behavioral validation. |
| Integration risks, not reproduced functional failures | Portal stacking, focus traps, scroll lock, editor interactions, React 19 third-party behavior | Mixed-component browser tests and representative workflows. |
| Unknown constraints | Actual browser support policy, delivery registry, performance budget, exact production feature priority | Product/engineering decisions and baseline measurements. |

There is no evidence of an unresolvable architectural blocker. These are tractable engineering and scope decisions. Conversely, it would be misleading to call the library ready for unrestricted Admin adoption today.

## 8. Planning sequence and completion criteria

1. **Prepare the external library boundary.** Decide React support, package/CSS delivery, fixed prefix, reset/token/root-unit/portal contract and supported browser baseline. Preserve the current standalone prototype experience through an explicit standalone stylesheet/setup if needed.
2. **Create an integration fixture before migrating a production route.** Use real legacy CSS and app-like chrome with an Elements button/input/dialog/combobox, an old react-select, and a long scrolling form. Verify old-only, new-only and mixed states; both import orders; portal placement; tab/escape/focus restoration; scroll lock; zoom; supported appearance modes; English and Spanish. The CSS audit in this report is an initial subset of that proof.
3. **Choose one bounded authenticated workflow.** Prefer a low-risk settings/detail form with ordinary inputs and a real save/error path. First prove production auth/query/permission integration without rebuilding it. A server-backed list should follow once its interface gap is closed; complex Inbox/editors are poor first pilots.
4. **Migrate by route/workflow with controlled shared-component rollout.** A global Buttons swap reaches 169 files, so a wrapper seam is not automatically low risk. Use a route/cohort flag and a known rollback version. CSS must also be gated/contained: turning off JSX does not undo globally loaded styles.
5. **Expand by capability.** Ordinary controls and feedback; dialogs/drawers; server lists and async fields; shell/navigation; complex editors/conversations. Track direct Bootstrap imports, indirect wrappers, selectors and public experiences separately.
6. **Remove React Bootstrap when runtime and type imports reach zero across the entire App package.** Public experiences currently skip admin CSS but may still use Bootstrap components. Separately prove that Bootstrap markup/descendant selectors and vendor styling dependencies have gone before removing the copied stylesheet. Retire Design's copy step/showcase when its consumers are accounted for. Other vendor retirements can follow their own justified plans.

Success means preserving data fetching and URL state, permissions, business callbacks, validation/submission, translations and accessibility while adopting Elements' approved appearance. Also measure bundle/CSS/font transfer and route load cost: both libraries, chart versions, date libraries and icon systems may coexist temporarily. No size reduction is established by this audit.

Validation needs more than a successful build. No test/spec files were found under Elements' apps/packages, and the UI package has no test script; its current checks do not establish behavioral regression coverage. Admin has substantial tests, but its TypeScript config excludes JS/JSX and test TSX files and disables strict mode, so typechecking alone cannot catch every changed wrapper contract. Use existing behavioral tests where relevant and add focused integration coverage around migrated workflows. [UI check scripts](</Users/liamyoung/Documents/Gecko Projects/elements-monorepo/packages/ui/package.json:6>), [App TypeScript scope](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/tsconfig.json:1>), [App test setup](</Users/liamyoung/Repos/Gecko-Admin-Web-App/App/vitest.config.ts:1>).

Effort is likely dominated by functional parity, coexistence and regression coverage, rather than the 60 direct-import files. Estimate only after the integration fixture and one real workflow reveal the cost per capability. A date or person-week estimate now would imply evidence we do not yet have.
