# Gecko Elements — Domain glossary

Terms used across the codebase and documentation. Implementation-free.

## Conversation

A transcript between one or more **administrators** and a **customer**. Appears in two places: the **inbox** (platform) and the **live chat widget** (embedded on customer websites).

## Administrator

The organisation-side participant in a conversation. Two subtypes:

- **Agent** — a human live-chat operator.
- **Bot** — an automated chat responder.

## Customer

The end-user side of a conversation — a potential student reaching out via email, widget, WhatsApp, Facebook, or another channel.

## Note

A message added by an agent that is visible only to administrators, never to the customer.

## System message

A message generated by the platform (not by a person or bot) — e.g. assignment changes, status updates.

## Inbox

The platform screen where agents view and respond to conversations. Contains a **chat head list** (left sidebar, always visible) and the active conversation.

## Live chat widget

A chat interface embedded on a customer's website. Contains a conversation with a reply box and message scroller.

## Chat head list

A left-aligned sidebar in the inbox showing one row per conversation. Always visible on desktop. Gecko is a desktop application; there is no mobile-specific layout.

## Bubble variant mapping (conversation roles)

- **Administrators** (agents + bots) use the **default** Bubble variant for their messages.
- **Customers** use the **secondary** Bubble variant for their messages.
- **Bot messages** use the **ghost** Bubble variant for their messages.
- **System messages** use the same Bubble variant as administrators.
- **Notes** (agent-only messages) use the **note** Bubble variant.

## Alignment rule (inbox vs widget)

Message alignment flips by _viewer_:

- In the **chat widget**, "your" messages are aligned **end** and the other participant's messages are aligned **start**.

## Reply box variants and where they apply

- The **default Reply box** is used in the **inbox** and other app-internal reply-box scenarios.
- The **basic Reply box** is used specifically in the **chat widget**, where Gecko needs only a simple text input plus send/actions.

### Header / footer placement rules

- The **header** is used exclusively in the **inbox**. It contains controls for changing channels.
- The **footer** can be used anywhere the **default Reply box** is used. Its controls are editable with presets depending on the selected channel type (for example, email channel controls).

## Typing indicator positioning

- The typing indicator is used in both the **inbox** and the **widget**.
- Both sides can see who is typing and when.
- It is rendered separately from the message transcript and stays fixed/in view at the bottom of the container.

## Emoji picker views

- The **tray** view is used for **reactions**.
- The **picker** panel view is used when inserting an **emoji into a message** (e.g. via the Reply box composer text), not for reactions.

## Transcript visibility and composition rules

- **Notes** and **system messages** appear in the same `MessageScroller` transcript as standard messages.
- **Notes** and **system messages** are never visible to customers.
- Channel switching is controlled only via the **Reply box header** (inbox-only control).

## Message scroller behavior rules

- Auto-follow to latest content only while the user is at the live edge.
- If the user scrolls away from the latest content, automatic snapping should stop and a return-to-latest affordance should be used.
- A "turn" anchor is the first message after sender streak changes (start of a new reply turn).

## Field

A layout wrapper for setup interfaces in Gecko — settings, event creation, and similar forms. Holds the label, helper text, and error message. Form primitives live inside Field.

### Validation

- When invalid, the error message appears in place of the helper text.
- Invalid fields change border, text, and hover/active states on the control.

### Disabled vs read-only

- **Disabled** — temporary; the value cannot be changed yet. Set on the control (`disabled`); Field may use `data-disabled` for layout styling.
- **Read-only** — the value is visible but not editable. Set on the control (`readOnly` on Input); Field does not own this state.

## Select family

- **Select** — short, fixed lists that do not need search.
- **Combobox** — longer lists where typing should filter options.
- **Native select** — reserved for student-facing surfaces (forms, events, live chat widget) where native mobile menu behaviour is preferred.
- **Search** — a product query that filters results elsewhere in the interface, not a form field or fixed-option picker.

## File upload surfaces

- **Attachment** — Gecko’s extended single-file upload field for forms and fieldsets; owns file selection, drag and drop, progress, retry, errors, completion, and removal in one row.
- **Drop zone** — large dedicated upload surface (for example, a hero image inside a dialog) where adding files is the only purpose.
- **File field** — not the primary Gecko pattern for in-form uploads; prefer Attachment.

## Sensitive field

Masks data by default. Values stay hidden unless explicitly revealed.

## Telephone field

Phone-specific formatting and validation. Not sensitive by default unless built that way.

## OTP field

Verification codes with auto-advance between slots and support for pasting the full value.

## Inline edit

In-place editing for headers, short single-line descriptions and applicable table-row values. The product owns persistence and validation.

## Input field

Single-line free-text control. Compose it with Field and a visible label in product forms; the product owns its value, validation and persistence.

## Number field

Exclusive use for numeric **quantities** — counts and amounts where stepper controls apply.

## Date field

Used for **date of birth** — segmented day/month/year input so people do not scroll back many years in a calendar.

## Date picker

Used for date fields that typically involve **future dates** — event dates, deadlines, and similar. Not for date of birth.

## Colour field

Used for **brand elements** — account colour, heading colour, widget colour, and similar branding settings.

## Checkbox and radio groups

- Default layout: vertical lists inside a group.
- **Button variant** (`asButton`): horizontal layout to draw attention to the selection.
- Validation errors appear on the **group**, not individual items.

## Form control sizing

No canonical size per surface. Use the component default unless a specific layout requires otherwise.

## App shell layout

Typical product layout (all pages except Inbox):

1. **AppHeader** (sandbox) — sticky top bar with account switcher, call/messaging status, and user account menu. Present on every page.
2. **AppSidebar** (sandbox) — app-wide main navigation. Present on every page. Built from the Sidebar primitives.
3. **Header** (page-level) — page title, breadcrumbs, actions, and optional sub-navigation tabs.
4. **Container** (page-level) — standardises spacing and layout for the main body.

**Inbox** is a custom layout: it does not use page-level Header or Container.

AppHeader and AppSidebar are documented under Structure. Both are compound `@gecko/ui` components:

- AppHeader — `AppHeader`, `AppHeaderLogo`, `AppHeaderActions`, `AppHeaderAccountSwitcher`, `AppHeaderControls`, `AppHeaderUserMenu`
- AppSidebar — `AppSidebar`, `AppSidebarFavourites`, `AppSidebarNav`

## Header and tabs

- **Header tabs** — sub-pages within a section that need sub-navigation.
- **Standalone Tabs** — sectioning content within a single page.

## Container

Every page should wrap its main body in Container for consistent spacing — except Inbox, unless stated otherwise.

## Sidebar vs Chat head

- **Sidebar / AppSidebar** — app-wide navigation only. Never a conversation list.
- **Chat head** — conversation list only (Inbox). Never app navigation.

## Breadcrumb

Breadcrumbs appear only inside the page-level Header. Header is consistent across the app except Inbox.

## Scroll area

Prefer Scroll area over native scroll wherever content is constrained — sidebar, container/main body, panels, and similar regions. AppHeader and AppSidebar stay sticky; Scroll area keeps overflow inside those fixed shells.

## Pagination

Used under **Data table** results for the most part, and also on **Activity feed** and other paginated data lists. Never in Header. Not used for app-wide search (Gecko has none).

## Separator

Purely presentational — divides functionality or data groups. Never carries semantic status (use Marker or similar for status in a thread).

## Inbox layout (exception)

Inbox does **not** use page-level Header or Container. Structure:

1. **Inbox-specific header** — navigation to inbox views (e.g. My conversations, Unassigned, Open, Closed, Sent, Assigned to bot, Undelivered), conversation search, and a filter control.
2. **Three-column grid:**
   - **Left — Chat head sidebar** — conversation list with list filters, sort, and new conversation.
   - **Centre — Conversation body** — contact name / assignment / conversation controls header, Message scroller transcript, Reply box.
   - **Right — Contact details panel** — accordion of contact metadata (details, activity, tasks, labels, notes, events, etc.).

AppHeader / AppSidebar remain; only the page body is custom.

## Naming: AppHeader vs Header

Keep the distinction: **AppHeader** = sticky product chrome; **Header** = page-level title bar (Elements).

## Feedback: Toast vs Alert vs Alert dialog

- **Toast** — ephemeral feedback after an action (success, error, or undoable outcomes).
- **Alert** — persistent, non-blocking callout within a page or section. The parent removes it when the condition ends; make it dismissible only when the message is safe to acknowledge and clear.
- **Alert dialog** — blocking confirmation for irreversible actions, especially **deletion**. Closing a conversation is reversible and must **not** use Alert dialog; prefer Toast with undo instead.

## Empty

Shown on any page where content would be listed but none exists yet — e.g. Data table pages for events, forms, broadcasts. Canonical composition: **icon + title + CTA**.

## Spinner vs Progress

- **Spinner** — indeterminate waits such as page or panel load.
- **Progress** — data / reporting display (how complete a metric or job is), not as the primary loading pattern for page waits.

## Table vs Data table

- **Data table** — default for product lists (events, forms, broadcasts, etc.) where filtering, sorting, actions, or pagination are needed.
- **Table** — simple, non-interactive tabular markup — e.g. reporting detail inside a Metric card — with no filtering or row actions.

## Filters

- Standalone **Filters** component; also wired into Data table as `DataTableFilters` via `toolbar.filters`.
- Pair product-list filtering with Data table. Filters may also control dashboard and reporting datasets without a table.
- Inbox / conversation filters are a separate product pattern — not the Filters + Data table composition.

## Metric card

Appears on dashboards, reporting, and individual product screens (e.g. an event’s success metrics). Typically laid out in **rows of three**.

## Card

May sit **inside** Container (e.g. chart blocks on a dashboard). Never wrap Container in a Card. Prefer Card for grouped dashboard content; Container owns page spacing.

## File tree

Not currently used in Gecko product UI. Intended for nested structures such as a website map for AI scraping. Do not invent other uses until product adopts it.

## Sortable list

Used when **reordering** elements is essential. Not for file upload (Drop zone / Attachment).

## Dialog vs Sheet vs Alert dialog

- **Dialog** — focused setup tasks (create/edit forms and similar). Blocks the page until finished. Used for everything that is not an action confirmation.
- **Sheet** — detail or side task that keeps page context visible behind it.
- **Alert dialog** — confirmation of an action only: deletion (required), navigating away with unsaved changes, and confirming a save. Not for general forms or content.

## Dropdown vs Context menu vs Popover

- **Dropdown menu** — actions that belong to a visible control (Data table row actions, Header menus, etc.).
- **Context menu** — exclusively on Data table (right-click / secondary pointer on rows).
- **Popover** — supporting content or controls on a trigger that are not an action menu (e.g. Filters, Colour field). Not for blocking decisions.

## Command

Not shipped in Gecko product UI yet. Do not invent app-wide command-palette usage until product adopts it.

## Tooltip

Icon-only buttons, truncated labels, Metric card help, and similar clarification. Never the sole place for required instructions.

## Button hierarchy

- **default** — primary action; usually one per Header / area.
- **outline** — the practical secondary button in Gecko (sandbox usage). Prefer outline over `secondary`, which is rarely used.
- **ghost** / **ghost-dark** / **ghost-light** — toolbar and icon chrome (including AppHeader).
- **destructive** — delete and other high-risk actions (still confirm irreversible deletes with Alert dialog).
- **ghost-destructive** — icon trash / remove controls (e.g. deleting a filter row).

## Badge

Primarily **status** in Data table columns (e.g. campaign Active) and **labels/tags**. Rarely used outside those patterns for now.

## Avatar / Avatar group

- Use Avatar whenever displaying a user (especially Data table “created by” columns).
- Use Avatar group when more than one person must show together (e.g. conversation assignees).
- Omit Avatar `size` for standard 32 px use. Use `md` in dense lists, data tables, and messages; reserve `2xl` and `3xl` for prominent account and profile displays.
- Avatar `status` owns the approved bottom-right availability badge. `notification` owns the top-left unread-activity badge; they may appear together.

## Counter

Compact counts — e.g. notification counts on or beside a Badge. Not for status labels or numeric form entry.

## Marker

Conversation-thread component related to Typing indicator. Use for: someone typing / AI composing, system messages (e.g. assignment changes), or a labelled separator in chat. Not a product-wide status Badge.

## Accordion

- **Default** Accordion reveals secondary information in dense panels, such as the Inbox contact-details panel. It is not a standard page-layout pattern.
- **Sectional** Accordion breaks large setup forms into meaningful sections to reduce cognitive load.
- Accordion is not page navigation. Page-level section switching uses Header tabs or standalone Tabs.

## Activity feed

Chronological history of actions on a contact, ordered newest first. Used in contact views and in the Inbox contact-details sidebar. Paginate when the history can grow long. Not for conversation transcripts (Message / Message scroller).

## Label

Always compose via Field (`FieldLabel`). Do not use Label as a standalone page heading.

## File field

Prefer Attachment for in-form uploads. File field is not the primary Gecko upload pattern.

## Calendar

Typically only inside Date picker for now. Date of birth still uses Date field.

## Code snippet

Customer-facing copyable snippets such as embed codes for websites (not a general docs-only primitive in product).
